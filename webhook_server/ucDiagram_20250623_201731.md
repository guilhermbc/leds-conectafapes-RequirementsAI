### Questions and Validations

As perguntas existentes são abrangentes e bem formuladas. Elas abordam lacunas críticas na compreensão do escopo do sistema, fluxos de trabalho, integrações e aspectos não funcionais. Nenhuma nova pergunta surgiu diretamente dos ajustes de prioridade, pois as perguntas existentes já cobrem a profundidade necessária para as prioridades ajustadas.

1.  **Clarificação de Papéis de Usuário:**
    *   Quais são os papéis e permissões específicos para "Pesquisadores" e "Empreendedores" dentro do Portal FAPs? Eles são tipos de usuários distintos, ou são subconjuntos de "Bolsistas" ou "Coordenadores" com tipos de projeto específicos? Atualmente, os casos de uso modelam apenas "Bolsista" e "Coordenador de Projeto".
    *   A equipe interna das FAPs (ex: administradores, controladores financeiros) terá acesso direto ao Portal FAPs, ou todas as suas interações serão exclusivamente através do Sistema Administrativo (ADM)? Se sim, quais são suas responsabilidades no Portal FAPs?

2.  **Fluxo de Trabalho de Gerenciamento de Documentos:**
    *   Quem é responsável pela validação dos documentos carregados (ex: equipe FAPs, automação do sistema, coordenador)?
    *   Qual é o fluxo de trabalho detalhado para validação de documentos? (ex: como a equipe FAPs acessa os documentos para revisão, como são registradas as aprovações/rejeições?).

3.  **Regras de Realocação de Bolsas:**
    *   Qual é o conjunto completo de regras e restrições que governam a realocação de bolsas (ex: número máximo de realocações, tipos específicos de bolsas que podem ser trocadas, limites orçamentários, impacto na duração do projeto)?

4.  **Fluxo de Efetivação de Remanejamento:**
    *   O caso de uso "Efetivar Remanejamento de Bolsas" menciona que o remanejamento pode exigir aprovação externa via ADM. Poderia detalhar o fluxo de aprovação? O Portal FAPs apenas envia a solicitação e aguarda uma resposta do ADM, ou há alguma interface para acompanhamento do status da aprovação dentro do Portal FAPs?

5.  **Troca de Dados com ADM (Envio):**
    *   O Portal FAPs precisa enviar outros dados de volta para o Sistema Administrativo (ADM) além das submissões de projetos e solicitações de remanejamento (ex: alocações de bolsas confirmadas, status de documentos, logs de atividade do usuário)? Se sim, quais dados e com que frequência?

6.  **Requisitos de Desempenho:**
    *   Quais são os requisitos de desempenho esperados para o sistema, tais como:
        *   Tempos médios/máximos de resposta para operações chave (ex: carregamento da visualização do projeto, realização de uma simulação)?
        *   Número esperado de usuários simultâneos (Coordenadores, Bolsistas)?
        *   Volume esperado de dados (número de projetos, bolsistas, documentos)?

7.  **Escopo do "Mínimo Mundo":**
    *   Poderia fornecer uma definição mais detalhada do escopo do "mínimo mundo" (produto mínimo viável) para o lançamento inicial do Portal FAPs? Quais funcionalidades são absolutamente essenciais para a primeira versão?

8.  **Relação com SigiFAPES:**
    *   Qual é a relação exata entre o Portal FAPs e o SigiFAPES? O SigiFAPES está sendo substituído, ou é um sistema que continuará a existir ao lado do Portal FAPs? Se for uma referência, quais funcionalidades ou padrões de design específicos do SigiFAPES devem ser adotados ou evitados?

9.  **Fluxo de Trabalho de Submissão de Projetos:**
    *   O caso de uso "Submeter Projeto" indica que o Portal FAPs lida com o formulário de submissão inicial e envia para o ADM para avaliação. Esta é a compreensão correta? Quais informações são coletadas no formulário de submissão e como são transferidas para o ADM para avaliação e aprovação?

10. **Disponibilidade do Sistema:**
    *   Quais são os requisitos de tempo de atividade esperados para o sistema (ex: 24/7, horário comercial)?
    *   Quais são os requisitos de recuperação de desastres e backup?

**Autenticar Usuário**
**Actors**: Bolsista, Coordenador de Projeto (Primário); Sistema de Autenticação Governamental (Secundário)
**Preconditions**:
*   O usuário possui uma conta válida no sistema de login do Governo do Estado (SOU GOV).
*   O sistema de login do Governo do Estado (SOU GOV) está disponível e acessível.
**Normal Flow of Events**:
1.  O usuário acessa a página de login do Portal FAPs.
2.  O sistema redireciona o usuário para a página de autenticação do Governo do Estado (SOU GOV).
3.  O usuário insere suas credenciais (usuário e senha) no sistema SOU GOV.
4.  O sistema SOU GOV valida as credenciais.
5.  O sistema SOU GOV notifica o Portal FAPs sobre o sucesso da autenticação.
6.  O Portal FAPs concede acesso ao usuário e o redireciona para a página inicial do sistema.
**Alternative / Exception Flows**:
*   **Credenciais Inválidas**: Se as credenciais inseridas no SOU GOV forem inválidas, o sistema SOU GOV exibe uma mensagem de erro e permite que o usuário tente novamente. Após múltiplas tentativas falhas (definido pelo SOU GOV), a conta pode ser bloqueada.
*   **Sistema SOU GOV Indisponível**: Se o sistema SOU GOV estiver indisponível, o Portal FAPs exibe uma mensagem de erro informando que a autenticação não pode ser realizada no momento.
*   **Usuário Não Cadastrado no Portal FAPs**: Se o usuário for autenticado pelo SOU GOV, mas não tiver um registro correspondente no Portal FAPs (como Bolsista ou Coordenador), o sistema pode redirecioná-lo para uma página de registro ou exibir uma mensagem de erro.
*   **Cancelamento**: O usuário pode cancelar a operação de login a qualquer momento antes da autenticação bem-sucedida, fechando a janela ou voltando à página anterior.
**Related Requirements**: RNF001

**Registrar Bolsista**
**Actors**: Bolsista (Primário)
**Preconditions**:
*   O usuário está autenticado no Portal FAPs (via SOU GOV) e não possui um perfil de Bolsista ativo.
*   O sistema está disponível para registro.
**Normal Flow of Events**:
1.  O Bolsista acessa a funcionalidade de registro de perfil de Bolsista.
2.  O sistema exibe um formulário de registro de Bolsista.
3.  O Bolsista preenche as informações pessoais solicitadas (nome, endereço, identidade, conta bancária, escolaridade, experiência, etc.).
4.  O sistema valida as informações inseridas conforme as regras de negócio (RN002, RN004, RN005, RN006, RN007).
5.  O Bolsista confirma o registro.
6.  O sistema registra o novo perfil de Bolsista no banco de dados.
7.  O sistema exibe uma mensagem de sucesso e redireciona o Bolsista para a página de gerenciamento de documentos ou perfil.
**Alternative / Exception Flows**:
*   **Dados Inválidos**: Se alguma informação inserida não atender às regras de validação (ex: idade menor que 18 anos, formato de CPF inválido, endereço fora do estado), o sistema exibe uma mensagem de erro específica para o campo e impede o prosseguimento até a correção.
*   **Informações Incompletas**: Se campos obrigatórios não forem preenchidos, o sistema exibe uma mensagem de erro e solicita o preenchimento.
*   **Bolsista Já Registrado**: Se o sistema identificar que o Bolsista já possui um registro ativo (ex: por CPF), exibe uma mensagem de erro e impede um novo registro.
*   **Erro no Registro**: Se ocorrer um erro interno ao tentar salvar os dados, o sistema exibe uma mensagem de erro genérica e solicita que o Bolsista tente novamente mais tarde.
*   **Cancelamento**: O Bolsista pode cancelar o registro a qualquer momento antes da confirmação, fechando a página ou clicando em "Cancelar".
**Related Requirements**: RF001, RN002, RN004, RN005, RN006, RN007

**Gerenciar Documentos**
**Actors**: Bolsista, Coordenador de Projeto (Primário)
**Preconditions**:
*   O usuário (Bolsista ou Coordenador) está autenticado no sistema.
*   O usuário possui um perfil ativo no sistema.
*   Existem tipos de documentos definidos e esperados para o perfil ou bolsa/projeto.
**Normal Flow of Events**:
1.  O usuário acessa a seção de gerenciamento de documentos.
2.  O sistema exibe a lista de documentos necessários e o status de cada um (pendente, enviado, em validação, aprovado, rejeitado).
3.  O usuário seleciona um tipo de documento para upload ou visualização.
4.  **Para Upload**:
    a. O usuário seleciona o arquivo do documento em seu dispositivo.
    b. O sistema carrega o arquivo.
    c. O sistema associa o documento ao tipo correspondente e atualiza seu status para "Enviado" ou "Em Validação".
    d. O sistema exibe uma mensagem de sucesso.
5.  **Para Reutilização (RF013)**:
    a. O usuário seleciona a opção de reutilizar um documento permanente previamente carregado.
    b. O sistema verifica a validade e aplicabilidade do documento.
    c. O sistema associa o documento existente ao novo contexto e atualiza seu status.
    d. O sistema exibe uma mensagem de sucesso.
6.  **Para Visualização (RF016)**:
    a. O usuário seleciona um documento já carregado.
    b. O sistema exibe o documento e seu status de validação, incluindo quaisquer comentários de rejeição.
**Alternative / Exception Flows**:
*   **Documento Inválido (Formato/Tamanho)**: Se o arquivo carregado não estiver no formato ou tamanho permitido, o sistema exibe uma mensagem de erro e impede o upload.
*   **Documento Rejeitado (RN003)**: Se um documento for rejeitado após validação (manual ou automática), o sistema atualiza o status para "Rejeitado" e exibe o motivo. O usuário pode então carregar uma nova versão do documento.
*   **Documento Duplicado**: Se o usuário tentar carregar um documento que já existe e está aprovado para o mesmo propósito, o sistema pode alertar ou impedir o upload, a menos que seja uma atualização.
*   **Erro no Upload**: Se ocorrer um erro durante o processo de upload (ex: conexão perdida), o sistema exibe uma mensagem de erro e solicita que o usuário tente novamente.
*   **Documento Permanente Não Aplicável/Expirado**: Se o usuário tentar reutilizar um documento permanente que não é aplicável ao contexto atual ou que perdeu a validade (se aplicável), o sistema exibe uma mensagem de erro.
*   **Ausência de Documentos Obrigatórios**: O sistema pode alertar o usuário sobre documentos obrigatórios que ainda não foram carregados ou validados.
**Related Requirements**: RF012, RF013, RF015, RF016, RN003

**Submeter Projeto**
**Actors**: Coordenador de Projeto, Bolsista (Primário)
**Preconditions**:
*   O usuário (Coordenador de Projeto ou Bolsista) está autenticado no sistema.
*   O usuário possui permissão para submeter projetos.
*   Existe um edital aberto e elegível para submissão de projetos.
**Normal Flow of Events**:
1.  O Coordenador de Projeto (ou Bolsista, se aplicável) acessa a funcionalidade de submissão de projeto.
2.  O sistema exibe um formulário para preenchimento dos dados do projeto (título, descrição, objetivos, orçamento, cronograma, etc.).
3.  O usuário preenche as informações do projeto.
4.  O usuário anexa quaisquer documentos adicionais exigidos para a submissão do projeto.
5.  O sistema valida as informações e documentos preenchidos.
6.  O usuário confirma a submissão do projeto.
7.  O sistema registra o projeto com status "Em Avaliação" e o envia para o Sistema Administrativo (ADM) para avaliação (RN009).
8.  O sistema exibe uma mensagem de sucesso e um número de protocolo para o projeto submetido.
**Alternative / Exception Flows**:
*   **Dados Incompletos/Inválidos**: Se campos obrigatórios não forem preenchidos ou as informações forem inválidas, o sistema exibe mensagens de erro e impede a submissão.
*   **Documentos Faltantes/Inválidos**: Se documentos obrigatórios não forem anexados ou estiverem em formato/tamanho incorreto, o sistema impede a submissão.
*   **Edital Fechado/Inexistente**: Se o edital selecionado (ou implícito) não estiver mais aberto para submissões, o sistema informa o usuário e impede a submissão.
*   **Erro na Comunicação com ADM**: Se houver falha na comunicação com o Sistema Administrativo (ADM) durante o envio do projeto, o sistema tenta novamente ou armazena o projeto localmente para envio posterior, notificando o usuário sobre o atraso.
*   **Projeto Duplicado**: Se o sistema identificar uma tentativa de submissão de um projeto já existente (com base em critérios definidos), ele alerta o usuário.
*   **Cancelamento**: O usuário pode cancelar a submissão a qualquer momento antes da confirmação.
**Related Requirements**: RF003, RN009
**Classes**:

**Visualizar Editais e Projetos Aprovados**
**Actors**: Coordenador de Projeto, Bolsista (Primário)
**Preconditions**:
*   O usuário (Coordenador de Projeto ou Bolsista) está autenticado no sistema.
*   Existem editais e/ou projetos aprovados cadastrados no sistema (via ADM).
**Normal Flow of Events**:
1.  O usuário acessa a seção de "Editais" ou "Meus Projetos".
2.  **Para Editais (RF004)**:
    a. O sistema exibe uma lista de editais disponíveis, com informações básicas como título, período de submissão e status.
    b. O usuário pode selecionar um edital para visualizar detalhes completos, incluindo regras, tipos de bolsas permitidas e verba total.
3.  **Para Projetos Aprovados (RF003)**:
    a. O sistema exibe uma lista dos projetos associados ao usuário (se Coordenador) ou aos quais o usuário é bolsista (se Bolsista), com status "Aprovado".
    b. O usuário pode selecionar um projeto para visualizar seus detalhes, como descrição, equipe, recursos e bolsas alocadas.
**Alternative / Exception Flows**:
*   **Nenhum Edital/Projeto Encontrado**: Se não houver editais ou projetos aprovados disponíveis para o usuário, o sistema exibe uma mensagem informando a ausência de dados.
*   **Erro na Recuperação de Dados**: Se ocorrer um erro ao tentar carregar os dados dos editais ou projetos, o sistema exibe uma mensagem de erro e solicita que o usuário tente novamente.
*   **Acesso Negado**: Se o usuário tentar acessar detalhes de um projeto ao qual não tem permissão (não é coordenador nem bolsista), o sistema nega o acesso e exibe uma mensagem de erro.

**Gerenciar Alocação de Bolsas**
**Actors**: Coordenador de Projeto (Primário)
**Preconditions**:
*   O Coordenador de Projeto está autenticado no sistema.
*   O Coordenador de Projeto possui projetos aprovados com cotas de bolsas disponíveis.
*   Existem bolsistas registrados e elegíveis para alocação.
**Normal Flow of Events**:
1.  O Coordenador de Projeto acessa a seção de gerenciamento de bolsas de um projeto específico.
2.  O sistema exibe uma visão geral das bolsas alocadas, incluindo os bolsistas (RF005, RF017), tipos de bolsa e duração (RF008).
3.  O sistema exibe as cotas de bolsas disponíveis para o projeto (RN001).
4.  O Coordenador de Projeto seleciona a opção de alocar uma nova bolsa.
5.  O sistema exibe uma lista de bolsistas elegíveis e tipos de bolsas disponíveis para alocação.
6.  O Coordenador de Projeto seleciona um bolsista e um tipo de bolsa.
7.  O Coordenador de Projeto informa a duração da bolsa.
8.  O sistema valida a alocação com base nas regras de elegibilidade do bolsista (RN002-RN007) e nas regras de alocação do projeto/edital (RN001, RN008).
9.  O Coordenador de Projeto confirma a alocação.
10. O sistema registra a alocação da bolsa ao bolsista no projeto.
11. O sistema atualiza a visualização das bolsas alocadas e as cotas disponíveis.
12. O sistema exibe uma mensagem de sucesso.
**Alternative / Exception Flows**:
*   **Bolsista Não Elegível**: Se o bolsista selecionado não atender aos requisitos de elegibilidade para o tipo de bolsa (ex: idade, escolaridade, certidões), o sistema exibe uma mensagem de erro e impede a alocação (RN002-RN007).
*   **Cota de Bolsa Esgotada**: Se não houver cotas disponíveis para o tipo de bolsa ou para o projeto, o sistema exibe uma mensagem de erro e impede a alocação (RN001).
*   **Regras de Alocação Violadas**: Se a alocação proposta violar outras regras específicas do projeto ou edital (ex: número máximo de bolsas por bolsista, duração máxima), o sistema exibe uma mensagem de erro (RN008).
*   **Erro no Registro**: Se ocorrer um erro interno ao tentar registrar a alocação, o sistema exibe uma mensagem de erro genérica.
*   **Cancelamento**: O Coordenador pode cancelar a alocação a qualquer momento antes da confirmação.
*   **Bolsista Já Alocado**: Se o bolsista já estiver alocado em uma bolsa que impede uma nova alocação (ex: não pode ter duas bolsas do mesmo tipo simultaneamente), o sistema impede a alocação.
**Related Requirements**: RF005, RF008, RF014, RF017, RN001, RN008

**Simular Remanejamento de Bolsas**
**Actors**: Coordenador de Projeto (Primário)
**Preconditions**:
*   O Coordenador de Projeto está autenticado no sistema.
*   O Coordenador de Projeto possui projetos com bolsas alocadas.
*   O sistema possui as regras de remanejamento de bolsas configuradas.
**Normal Flow of Events**:
1.  O Coordenador de Projeto acessa a funcionalidade de "Simulação de Remanejamento" para um projeto específico.
2.  O sistema exibe a configuração atual das bolsas do projeto e os recursos/cotas disponíveis.
3.  O Coordenador de Projeto seleciona as bolsas que deseja remanejar (ex: trocar uma bolsa de maior valor por duas de menor valor, alterar tipo de bolsa, ajustar duração).
4.  O Coordenador de Projeto insere os parâmetros da simulação (ex: novos tipos de bolsa, novas durações, novos bolsistas se aplicável).
5.  O sistema processa a simulação com base nas regras de negócio de remanejamento.
6.  O sistema exibe os resultados da simulação (RF019), mostrando o impacto nos valores das bolsas, cotas e recursos restantes (RF011).
7.  O Coordenador de Projeto pode ajustar os parâmetros da simulação e refazer a simulação quantas vezes desejar.

*   **Dados Incompletos para Simulação**: Se o Coordenador não fornecer todos os parâmetros necessários para a simulação, o sistema solicita as informações faltantes.
*   **Erro no Processamento da Simulação**: Se ocorrer um erro interno durante o cálculo da simulação, o sistema exibe uma mensagem de erro genérica.
*   **Nenhuma Bolsa para Remanejar**: Se o projeto não tiver bolsas alocadas, o sistema informa que não há simulações possíveis.

**Efetivar Remanejamento de Bolsas**
**Actors**: Coordenador de Projeto (Primário)
**Preconditions**:
*   O Coordenador de Projeto está autenticado no sistema.
*   O Coordenador de Projeto tem permissão para efetivar remanejamentos.
*   As regras de negócio para remanejamento são atendidas.
**Normal Flow of Events**:
1.  O Coordenador de Projeto acessa a funcionalidade de "Remanejamento de Bolsas" para um projeto específico.
2.  O Coordenador de Projeto define as alterações de remanejamento (diretamente ou a partir de uma simulação salva).
3.  O sistema valida as alterações propostas em relação às regras de negócio (ex: orçamento, cotas, elegibilidade).
4.  O sistema exibe um resumo das alterações e solicita confirmação.
5.  O Coordenador de Projeto confirma a efetivação do remanejamento.
6.  O sistema aplica as alterações no registro das bolsas e atualiza os recursos e cotas do projeto.
7.  O sistema registra a transação de remanejamento.
8.  O sistema exibe uma mensagem de sucesso.
**Alternative / Exception Flows**:
*   **Remanejamento Inválido**: Se as alterações propostas violarem alguma regra de negócio (ex: exceder orçamento, violar limites de cotas, tentar remanejar para um tipo de bolsa não permitido), o sistema exibe uma mensagem de erro e impede a efetivação.
*   **Aprovação Necessária**: Se o remanejamento exigir aprovação externa (ex: da FAPs via ADM), o sistema envia a solicitação de remanejamento para aprovação e atualiza o status para "Pendente de Aprovação". O remanejamento só é efetivado após a aprovação.
*   **Erro na Efetivação**: Se ocorrer um erro interno ao tentar aplicar as alterações, o sistema reverte a operação (se possível) e exibe uma mensagem de erro genérica.
*   **Cancelamento**: O Coordenador pode cancelar a efetivação a qualquer momento antes da confirmação final.
**Related Requirements**: RF009

**Receber Dados do Sistema Administrativo**
**Actors**: Sistema Administrativo (ADM) (Primário)
**Preconditions**:
*   O Sistema Administrativo (ADM) está operacional e configurado para enviar dados ao Portal FAPs.
*   O Portal FAPs está disponível e com sua interface de integração ativa.
**Normal Flow of Events**:
1.  O Sistema Administrativo (ADM) inicia o envio de dados (ex: novos editais, atualizações de projetos, aprovações de submissões).
2.  O Portal FAPs recebe os dados do ADM através da interface de integração (RNF002).
3.  O Portal FAPs valida a integridade e o formato dos dados recebidos.
4.  O Portal FAPs processa os dados e os armazena/atualiza em seu banco de dados (ex: cadastra novos editais, atualiza status de projetos para "Aprovado" - RN009).
5.  O Portal FAPs envia uma confirmação de recebimento e processamento ao ADM.
**Alternative / Exception Flows**:
*   **Dados Inválidos/Inconsistentes**: Se os dados recebidos do ADM forem inválidos ou inconsistentes (ex: formato incorreto, dados faltantes), o Portal FAPs rejeita os dados, registra o erro e notifica o ADM sobre a falha (RNF005).
*   **Falha na Conexão**: Se a conexão entre o ADM e o Portal FAPs falhar, o Portal FAPs não recebe os dados e o ADM pode tentar reenviar posteriormente.
*   **Erro no Processamento Interno**: Se ocorrer um erro interno no Portal FAPs durante o processamento dos dados (ex: falha no banco de dados), o sistema registra o erro e notifica o ADM sobre a falha no processamento.
*   **Dados Duplicados**: Se o ADM enviar dados que já existem no Portal FAPs e não são atualizações, o Portal FAPs pode ignorar ou registrar como um aviso, dependendo da regra de negócio.
*   **ADM Indisponível**: Se o ADM não conseguir iniciar o envio de dados, o Portal FAPs não receberá as informações.
**Related Requirements**: RF003, RF004, RNF002, RN009
